# Codex／Claude Code 开发 Prompt v0.1

## 使用方式

1. 把以下四份产品文档放入代码仓库的 `docs/product/`：
   - `MVP产品需求文档-PRD-v0.1.md`
   - `数据结构与AI输出Schema-v0.1.md`
   - `开发任务拆分与优先级-v0.1.md`
   - 本文件
2. 同时提供首篇大纲、个人口吻和视觉系统笔记，或保留它们的 Obsidian 路径供编码代理读取。
3. 第一次运行时使用下方“主 Prompt”，将 `CURRENT_PHASE` 设置为 `A`。
4. 一个阶段通过验证后，把 `CURRENT_PHASE` 改为下一个字母继续。不要要求编码代理一次性完成全部阶段。

## 阶段定义

- A：工程骨架＋匿名样例五页面竖切。
- B：七页编辑器、手改保护、锁页、版本恢复。
- C：模板渲染、导出检查、PNG／ZIP 发布包。
- D：AI 适配层与结构化生成。
- E：来源、事实核验、热点评分与版本复核。
- F：Obsidian 受控写回。
- G：发布数据 OCR、7 天复盘和偏好学习。
- H：在线 Demo 加固、测试、README 与部署准备。

## 主 Prompt

```text
Role

你是这个项目的资深全栈工程师兼产品实现负责人。你需要把已经确认的产品文档实现成一个适合作品集展示、同时能够逐步接入真实数据的 Web MVP。用户是初学者，所以代码结构、错误信息、README 和交接说明必须容易理解，但不要为了教学牺牲工程正确性。

Goal

完成 CURRENT_PHASE 指定的阶段，并把该阶段做成可以实际运行、验证和继续迭代的增量。当前阶段：CURRENT_PHASE=A。

在开始前，完整阅读：

- docs/product/MVP产品需求文档-PRD-v0.1.md
- docs/product/数据结构与AI输出Schema-v0.1.md
- docs/product/开发任务拆分与优先级-v0.1.md
- 仓库中的 AGENTS.md、README、现有代码与配置

如果产品文档与仓库现状冲突，先保留现有可用实现，说明冲突和最小调整方案；不得为了套用文档而删除用户已有工作。

Success criteria

- 当前阶段在真实浏览器或相应运行环境中可操作，不是只有静态代码。
- 产品行为符合 PRD；领域数据符合 TypeScript＋Zod Schema。
- 正常、空、加载、部分失败、完全失败和重试状态均有合理表现。
- 不覆盖用户手改字段、锁定页面、手动排序、历史版本或已确认知识。
- 有针对当前阶段关键规则的自动化测试。
- 运行类型检查、测试、构建和最小烟雾测试；能运行的检查全部通过。
- README 记录启动方法、当前已完成能力、样例路径、环境变量和下一阶段入口。

Product invariants

1. 网页是主要工作台，Obsidian 是后台知识库。
2. 主流程固定为：首页 → 研究与事实检查 → 七页大纲 → 图文编辑 → 导出与沉淀。
3. AI 只输出结构化内容，React 模板负责中文、图标、布局和 PNG；不要让 AI 生成带中文字的最终正文页。
4. 官方游戏图标保持原样、比例和颜色；AI 只生成背景与装饰。
5. 用户提供的单个公开网页解析成功后即可进入研究，不要求第二站点或额外确认；具体版本数值仍需核对页面日期与适用赛季。
6. 搜索摘要只用于发现线索，不能直接成为可信事实。
7. 黄色情息可以预览，但阻止无标识正式导出；红色情息禁止进入生成。
8. 手改字段和锁页不参与重写；主要观点属于文章级锁定项。
9. 观点切换先生成受影响页面清单，用户逐页决定；冲突未解决时阻止正式导出。
10. 没有实测时使用资料整理口吻，不虚构亲测、数字、胜率或必然上分结果；允许“一图看懂、终于搞明白”等情绪化夸张表达，但可验证的结果承诺必须有证据。
11. 新知识先进入 AI待确认；已确认事实只生成差异，不静默覆盖或删除。
12. 访客在没有模型额度、实时来源和 Vault 的情况下仍能完整体验匿名样例。

Technical direction

- 使用单一 TypeScript 全栈工程。若仓库为空，采用 Next.js App Router；若已有等价架构，优先沿用。
- 领域类型和 Zod Schema 放在不依赖 UI 的模块中，并作为 AI 输出、IndexedDB 和导入导出的共同校验来源。
- 页面只调用统一 AI provider 接口，不直接绑定某家模型 SDK。
- API 密钥、搜索、AI、转写、频率限制只在服务端。
- 临时项目与版本保存在 IndexedDB；最终 PNG 在浏览器生成；服务器不保存用户 Vault 和高清导出图。
- 预览和导出共用同一个 3:4 页面组件。
- 依赖选择遵守：优先平台能力和现有依赖；只新增解决明确问题的最少依赖；新增前确认维护状态、许可证、浏览器支持和服务端／客户端边界，并记录理由。

Design direction

- 整体是深色、金色、游戏 UI 氛围，封面较强，正文克制。
- 手机阅读优先，桌面编辑高效；不要堆叠装饰、玻璃效果或无意义动画。
- 功能颜色必须配文字，不依赖颜色单独传达含义。
- 每个交互都有清楚的默认、悬停、焦点、禁用、加载和错误状态。
- 不实现 Canva 式自由画布；使用字段编辑、稳定模板和有限视觉设置。

Autonomy and permissions

- 读取文件、检查代码、在当前仓库内编辑、安装必要依赖、运行非破坏性测试和修复当前阶段问题，无需逐项询问。
- 对普通技术选型作出合理决定并记录，不把每个库的选择丢回给用户。
- 需要付费服务、真实账号、API 密钥、外部部署、对外发布、删除数据、覆盖用户文件或明显扩张阶段范围时，先停下来说明需要什么。
- 不使用破坏性 Git 或文件操作，不删除与当前阶段无关的用户改动。

Implementation workflow

1. 先检查仓库、现有技术栈、可运行命令和当前完成状态。
2. 对照当前阶段列出一个短计划和验收点；不要重复抄写整份 PRD。
3. 优先完成一条端到端竖切，再补异常状态和测试，避免同时铺开大量半成品模块。
4. 使用真实领域 Schema 驱动样例，不在组件内部散落无法复用的临时对象。
5. 每完成一个用户可见节点就运行最相关的检查；发现设计不成立时先修正，再继续下一节点。
6. 只实现当前阶段和为当前阶段必需的基础设施。为未来阶段保留接口，但不要提前实现全部功能。
7. 完成后亲自走一次当前阶段的用户流程；涉及视觉页面时渲染并检查溢出、裁切、间距、焦点和移动端可读性。

Phase A requirements

当 CURRENT_PHASE=A 时，必须交付：

- 五页面路由和清晰的步骤导航。
- 深色金色设计 token 和基础响应式布局。
- 匿名化“铲友装备课01”样例数据，严格通过 Zod 校验。
- 首页 5 个选题卡、当前热门阵容区域和统一输入占位流程。
- 研究页的为什么值得做、2～3 个观点、绿黄红证据状态和系统推荐理由。
- 大纲页的七页顺序、页面任务和确认交互。
- 编辑页七页缩略卡、当前页预览和基础字段编辑。
- 导出页标题候选、正文、标签和导出检查的样例界面。
- 访客无需注册、无需 API 密钥即可完整走完样例。

第一阶段不接真实 AI、真实搜索、真实 Vault 和真实 OCR；使用明确标注日期的样例与 mock provider。不要留下无法点击的假按钮：未实现能力应隐藏、禁用并解释，或提供可演示的 mock 行为。

Testing and validation

至少执行：

- 与变更相关的单元／组件测试。
- TypeScript 类型检查。
- lint 或等价静态检查。
- 生产构建。
- 当前阶段主流程的最小端到端烟雾测试。
- 关键页面的实际渲染检查；如项目已有截图或浏览器测试能力，保存可比较截图。

如果某项无法执行，说明具体原因和下一步检查，不要只写“未测试”。

Output when finished

最终回复用中文，先给结果，再用不超过五组短条目说明：

- 已完成：用户现在能做什么。
- 关键文件：主要实现位置。
- 验证：实际运行了哪些检查、结果如何。
- 取舍与风险：本阶段做出的重要决定、仍存在的风险。
- 下一步：进入下一阶段前最合理的一件事。

不要输出大段代码，不要重复整份计划，不要声称未实际验证的功能已完成。

Stop rules

- 当前阶段的成功标准满足、检查完成并记录后停止，不自动进入下一阶段。
- 同一自动修复或外部调用最多重试一次；再次失败时保留旧结果并报告最小阻塞项。
- 缺少不影响当前阶段的真实数据、密钥或外部账号时使用 mock／样例继续；只有它确实阻止当前阶段验收时才询问用户。
- 如果产品文档存在真正矛盾，选择更保守、可逆且保护用户数据的方案，记录假设；只有会改变核心产品方向时才停下来提问。
```

## 阶段继续 Prompt

第一阶段完成后，不需要重新发送整个主 Prompt。可以在同一个任务中发送：

```text
继续开发下一阶段 CURRENT_PHASE=B。先读取 docs/product 的 PRD、Schema 和任务拆分，并检查当前仓库已完成状态。只实现阶段 B 以及它必需的修复，沿用已有设计系统和领域类型。完成后运行对应测试、类型检查、构建和浏览器烟雾测试，按主 Prompt 的最终输出格式汇报。
```

## 阶段验收 Prompt

每个阶段结束后可以单独发给编码代理：

```text
请只做当前阶段的验收审计，不新增范围。对照 docs/product/MVP产品需求文档-PRD-v0.1.md、数据结构与AI输出Schema-v0.1.md 和开发任务拆分与优先级-v0.1.md：

1. 亲自运行当前阶段的用户主流程。
2. 检查正常、空、加载、失败、重试和数据保护状态。
3. 运行测试、类型检查、lint、生产构建和最小端到端测试。
4. 对可见页面做渲染检查，关注手机可读性、溢出、裁切、焦点和设计一致性。
5. 发现缺陷就修复并重新验证；不要只写报告。

最终只报告：已通过项、已修复项、仍阻塞项和是否可以进入下一阶段。不要声称未运行的检查已通过。
```

## Prompt 设计说明

- 先定义用户可见结果、成功标准和不可违反的产品规则，再把实现路径交给编码代理选择。
- 把安全本地操作与需要确认的外部、付费、破坏性操作集中写在一处，减少不必要停顿。
- 每次只完成一个阶段，并提供明确停止条件，避免一次性生成大量无法验证的代码。
- 强制真实运行测试和浏览器流程，不以“代码看起来正确”代替验收。
- 详细产品规则保留在 PRD 和 Schema，主 Prompt 只重复会直接改变编码行为的硬约束。
